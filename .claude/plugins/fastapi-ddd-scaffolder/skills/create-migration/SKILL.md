# Create Alembic Migration

<task>Take a model change from code to database: verify registration, autogenerate the revision, review it, then apply it.</task>

Existing revisions:

!`ls migrations/versions`

## Scope

- **In scope:** registration check, autogenerate, review, apply.
- **Out of scope:** changing the model. If the review shows the model is wrong, stop, fix the
  model, and regenerate — never patch the revision to compensate.
- **Done when:** the revision is applied, the schema matches, and ruff is clean.

Copy this checklist and tick it off:

```
Migration progress:
- [ ] Model registered in migrations/env.py
- [ ] Database reachable and at head
- [ ] Revision autogenerated
- [ ] Revision reviewed
- [ ] Applied
```

## Step 1 — Verify registration

Read `migrations/env.py`. Every model whose table should exist must be imported there and present
in the `_ = [...]` list. Add the missing import and list entry, keeping both alphabetical.

This check is not optional: autogenerate only sees registered models, and an unregistered model
whose table already exists makes autogenerate emit a `drop_table` for live data.

## Step 2 — Check the database state

```bash
uv run alembic current
```

If the database is behind, run `uv run alembic upgrade head` first — autogenerate compares against
the live schema and produces a wrong diff otherwise.

`migrations/versions/` ships empty in this template. On a fresh project the first autogenerate
produces the whole initial schema in one revision; that is expected.

## Step 3 — Autogenerate

```bash
uv run alembic revision --autogenerate -m "<snake_case_description>"
```

Message conventions: `create_{entity}_model`, `create_{a}_and_{b}_models`, or an imperative
phrase for an alteration (`add_expires_at_to_keys`).

`make migration m="<description>"` wraps the same command.

## Step 4 — Review the generated file

Read the new file under `migrations/versions/`. Autogenerate produces a draft, not a decision.

```
- [ ] down_revision chains to the current head (no branching)
- [ ] Table names carry the APPLICATION_TABLE_PREFIX
- [ ] Constraint and index names follow uq_/ix_/ck_{plural}_{cols}
- [ ] Enum columns emit sa.Enum('MEMBER_A', 'MEMBER_B', name='{snake}_enum')
- [ ] Column comments came through
- [ ] downgrade() drops indexes before tables, in reverse dependency order
- [ ] No spurious diffs (server-default noise, type churn)
- [ ] No unrelated drop_table — that means a model is missing from env.py
```

PostgreSQL stores enum member **NAMES** in uppercase, so any data operation in a migration must
use `'ADMIN'`, not `'admin'`.

By project convention `downgrade()` drops tables and indexes but does **not** drop PG enum types.
If a revision is rolled back and regenerated, drop the orphaned type manually
(`DROP TYPE IF EXISTS {name}`) before re-upgrading, or the new upgrade fails on a type that
already exists.

## Step 5 — Apply

```bash
uv run alembic upgrade head
```

Confirm the `Running upgrade` line. Then check the schema landed:

```bash
uv run python -c "
from sqlalchemy import text
from app.core.database import pg_engine
with pg_engine.connect() as c:
    print(c.execute(text(\"SELECT column_name, is_nullable FROM information_schema.columns WHERE table_name='<full_table_name>' ORDER BY ordinal_position\")).fetchall())
"
```

Finally, `uv run ruff check migrations` — generated files must lint clean.

## Rules

- Always autogenerate schema migrations. A hand-written schema revision drifts from the models,
  and nothing detects the drift.
- One logical change per migration. Batching unrelated model edits makes a partial rollback
  impossible.
- Never edit an applied migration. For a local-only mistake: `downgrade`, drop any orphaned enum
  types, delete the file, fix the model, regenerate.
- The app runs `alembic upgrade head` on startup (`core/migrations.py`), so an unreviewed revision
  left in the tree will be applied by the next boot. Review before leaving the file in place.
- Data seeds are separate, hand-written revisions — see
  [`create-seed-migration`](../create-seed-migration/SKILL.md). Never mix schema and data in one
  file.
